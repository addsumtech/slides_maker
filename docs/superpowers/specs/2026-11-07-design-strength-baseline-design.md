# 设计能力不被削弱：以网站 12 份示例为基准的对照、修复与守门

日期：2026-11-07 · 状态：待用户审阅

## 1. 为什么做

slide-maker 早期能做出大胆、新颖的设计。此后不断加入新内容：数字回查、进度提示、闸门手续、品牌步骤。SKILL.md 现在约 325KB（约 8 万 token）。用户担心的是：新内容越堆越多，原来的设计能力被挤掉、变弱了。要做的事是**证明有没有变弱，变弱了就找回来，并且以后加东西时不再变弱**。

基准由用户指定：网站上那 12 份示例 deck（slides.addsum.top，文件在 `~/code_project/slides_maker-site/templates/decks/{zh,en}/<id>/`，每份含 `template.pptx`、`render/slideNN.png`、`profile.md`）。这 12 份大多在 2026-07 前后做成。

### 已有线索（2026-11-07 实测，证据见下）

1. **11-05 实跑成品**（Codex 路径，虚构的临江社区卫生服务中心年报，9 页）对比基准，差距明显：
   - 9 页里有 6 页是"标题 + 一排卡片"；
   - type drama（最大字号 ÷ 正文中位数）是 3.3×，基准 4 份是 5.0–11.8×；
   - 视觉语言是 null，imagery 是 none。
2. **原因来自那次的 friction log**：
   - SKILL.md 读不完，agent 跳过了 Step 4 约 1000 行的组件目录（F4）；
   - 示例脚手架是 .py，agent 的规则不允许读源码（F3）；
   - `card_dominance` 和 `size_sprawl ×9` 被写 waiver 放行（G2）；
   - 构图竞争只比了封面。
3. **现有测量本身有盲点**：
   - lint 的 `distinct skeletons` 给这份明显重复的 deck 报 9/9，等于没看出重复；
   - 现行 lint 对基准示例报大量 hard finding（chengdu 58、kids 108、launch 35，quarterly 0），其中真假混杂：
     - chengdu 封面页脚字确实看不见，这是真缺陷；
     - kids 封面那个用形状拼成的机器人，被报了一堆 OVERLAP（未成组），这是误报；
   - 规则会把 agent 从基准的做法上推开，例如 12pt 正文、10 档字号的密集看板都会触发 SIZE SPRAWL 和 TEXT WALL。这条是推测，Phase 1 要核实。
4. **8-17 巴黎 deck 同样单调。** 所以"老版本一定更强"没有证据，必须实跑对照，不能凭印象下结论。

## 2. 目标 / 非目标 / 反目标

**目标**
- G1 用实跑回答：现在的 skill，在与基准同样的内容和素材下，设计强度是否明显低于基准；低在哪里，原因是什么。
- G2 只修实测到的缺口。用户已选的三项（组件总览图 + 推荐、内页构图竞争 + 骨架重复、无照片图像方案）在缺口确实存在时实施。
- G3 留下一个设计守门员，以后大改时能发现设计退化。
- G4 修完后用同一批 brief 重跑，给出改前改后对照。

**非目标**
- 不重做 12 份示例，不改网站。
- 不在这次精简 SKILL.md 全文，只挪动和设计相关的段落（见 §4.2）。
- 不解决与设计无关的手续问题，例如记录格式文档、codex-runtime 编号。

**反目标**（做了也算失败）
- 给 agent 增加新的手续或 waiver 负担。设计能力被削弱的一个原因就是手续挤占注意力。
- 新的或加严的检查在 12 份基准上误报。基准能过，是新检查的硬性前提。
- SKILL.md 净增长。要加内容，就从别处挪出等量的内容。
- 只凭"闸门全绿"或单元测试宣称变好了，必须看渲染图和对照结果。

## 3. 约束

- **成本**：不花付费 API。实跑和评审用 Sonnet subagent，Codex 路径用 codex 订阅（免费档没有出图工具）。
- **测试素材**：示例 deck 是 skill 自己的示例，不是用户的文件，可以用。不用用户自己的 deck。测试用隔离的 `SLIDE_MAKER_REGISTRY`，不写 `~/.claude/slide-templates`。
- **Git**：commit 到本地。推送要用户在当次请求里明确说。暂存时点名文件路径。
- **安装副本**：skill 改动后 rsync 到 `~/.agents/skills/slide-maker/`。
- **交付**：给用户看的对照报告放 `~/Desktop`。
- 回复用户用中文。

## 4. 怎么做

### Phase 1 — 对照测量（先做，结果给用户看过再进入 Phase 2）

**选样**（我的决定）：从 12 份里挑 4 份，覆盖不同的设计取向：
- `zh/quarterly-review`：数字密集、瑞士网格、无图；
- `zh/chengdu`：图像主导；
- `zh/product-launch`：发布会、大字冲击；
- `zh/kids-ai-explainer`：形状拼成的插画角色、儿童向。

只做中文版。

**输入**：从每份 `template.pptx` 抽出内容材料，做成一份"素材文档"：
- 每页的文字和数字，按原顺序排；
- 原 deck 用到的图片原样作为素材文件提供，保证"有没有图可用"这一条和基准相同；
- 附一份"测试材料说明"：受众、场合、时长，取自 `profile.md` 的适用场景；
- **不给任何设计信息**：不给配色、字体、版式描述，不给 profile.md 的设计部分。

素材按原顺序排，但只是一个内容池：agent 可以照常走内容规划，自己决定页数和每页结构。不强制逐页照搬，因为 11-05 那份就是在规划这一步塌成"标题 + 卡片"的，这一步必须测到。所以对照比的是整份 contact sheet，不逐页配对。（我的决定）

**三组对照**（用户决定加老版本组）：
- **基准**：网站上的 12 份示例之 4。它们很可能反复打磨过，代表天花板。
- **老版本 v4.2.0**：这批示例做成时的版本（2026-07-28 发布）。从 git tag 导出到隔离目录运行，不碰安装版。
- **现在版**：当前安装版。

"老版本 vs 现在版"回答"有没有退化"；"现在版 vs 基准"回答"离天花板多远、差在哪"。

**运行**：
- 每组 4 份 × 每份 1 次，共 8 个 Sonnet agent，分两批并行。都是 Claude 路径、auto 模式（跳过访谈），每个用独立的 registry。
- 另加 1 个"Codex 式"文档路径：Sonnet agent 只读文档、不读源码，只跑命令输出里给的下一步，这和 11-05 的做法一样。用 quarterly-review、现在版。不用 `codex exec`，因为 auto 模式之前拒绝过。
- 嵌套的独立评审 agent 起不来时，照例写 critic-independence waiver，两组条件相同。
- 不出图，只用提供的原图（codex 免费档没有出图工具，两组条件相同）。
- 记录完整 transcript。
- 每份只跑 1 次，噪声大。所以结论只报"一致的方向"，单对的差异不下结论。（我的决定）

**渲染**：基准的 `template.pptx` 和两组实跑都用当前同一条渲染管线重新渲染，不用网站上的旧 PNG，避免渲染器版本差异混进评分。（我的决定）

**对照方法**：
1. **盲评**：另起 Sonnet agent，每次看两张不标来源的 contact sheet（基准 vs 实跑，左右随机）。按 5 项打分并说理由：大胆/新颖、骨架多样性、视觉层级/重心、组件与数据图形的贴切度、细节工艺；最后给出整体偏好。每对评两次、交换左右，取一致结论。
2. **自动指标**：两边各算一遍
   - type drama；
   - 骨架多样性（用 `composition_probe` 的签名两两比较，算"相似对的占比"。现有 `distinct skeletons` 是瞎的，不用）；
   - 命名组件数与手搭 box 的比例（`component_audit`）；
   - card dominance、envelope monoculture；
   - 是否有图像或插画；
   - 有没有一页明显比其他页更突出（以最大元素面积和字号的离群程度近似）。
3. **原因定位**：读每个实跑的 transcript，记三件事：读了哪些设计相关文件、跳过了哪些；哪些设计警告被写了 waiver；在哪里退回到卡片或 box 的做法。

**产出**：`~/Desktop/slide-maker-设计对照-2026-11-07/`，内含：
- 每对的并排图；
- 指标表；
- 盲评结论；
- 原因清单。

盲评同时做"老版本 vs 现在版"和"现在版 vs 基准"两组配对。

**分支**：
- **退化**：老版本在盲评里多数胜出（4 对里至少 3 对，两次交换左右都一致），或指标一致偏向老版本。这说明确实被削弱了，原因清单里的"后来加的东西"优先修。
- **没退化，但离基准远**：差距来自"一次性 vs 打磨"，修复重点放在送达和构图上，让一次性运行更接近打磨版。
- 两种情况都把结果和 Phase 2 的修复顺序给用户确认后再动手。

**完成标准**（用户决定）：一轮修复 + 复测。复测时盲评和指标都比修前好，就收尾；与基准的剩余差距如实写进报告，不追求追平。

### Phase 2 — 修复（只修 Phase 1 测到的缺口）

每项先盘点现有能力，避免重复造。已知现有能力：
- 地图：`deckkit.choropleth`、`maps.py`；
- 计数格：`deckkit.unit_grid`；
- 装饰：`ornaments.py`；
- 构图签名：`composition_probe.py`；
- 组件审计：`component_audit.py`；
- 成组可以豁免 OVERLAP（lint 把 group 当一个整体）。

候选修复，按 Phase 1 的结果取舍：

1. **组件送达**（对应"组件总览图 + 推荐"）
   - 生成一张组件总览图：按内容形状分类，每类配 2–3 个组件的真实渲染缩略图，加组件名和一行用法。图由脚本从 deckkit 现场渲染，不手画，保证和库同步。内容形状包括 KPI、趋势、构成、前后对比、目标进度、排名、流程、时间线、地理、计数、引言、人物/角色。
   - 推荐脚本：读内容计划（每页的论点和数据形状），给每页推荐组件和调用签名。
   - 送达位置要放在 agent 一定会碰到的地方：内容计划完成后的那条命令输出、`deck_cycle` 首次构建前的提示、Codex 路径文档的对应步骤。不能只放在 SKILL.md 的长目录里。
2. **内页构图与骨架重复**（对应"内页构图竞争 + 骨架重复"）
   - 构图竞争从"只比封面"扩展到"封面 + 2 张关键内页"。关键内页由内容计划里分量最重的页决定。沿用一次渲染多变体，成本几乎不增加。
   - 一个看得出重复的骨架指标：基于 composition_probe 签名的相似度。
     - 正例：24 份基准（中英文都算），必须全部通过。
     - 负例：临江年报（虚构材料，复制进仓库做测试夹具），以及 Phase 1 里盲评判为弱的实跑成品。（我的决定）
     - 只有找得到一个阈值能把两边分开时才做成阻断，出路是改版面，不提供"写一句话就放行"的 waiver；确有理由时用现有的 `design_intent` 声明。
     - 分不开就降级为警告（advisory），并在报告里说明。不会为了能阻断而去放松基准。（我的决定）
3. **无照片图像**（对应"无照片图像方案"）
   - 盘点后补缺。候选：人形 pictogram 阵列（可能是 `unit_grid` 的一个参数）、形状拼接的插画角色和场景套件（参照 kids 示例的机器人，**输出为 group**，避免误报 OVERLAP）、简化区位图。
   - 规则配套：没有照片素材、也没有出图工具时，内容计划要明确选一种无照片图像方案，或者给出不用的理由。这条要看 Phase 1 是否显示"无图 → 全卡片"确实是原因之一。
4. **规则对基准的误伤**（Phase 1 若证实）
   - 若有 hard/阻断检查在基准的有意设计上误报，修检查本身，不是让基准改。例如未成组的拼接插画、密集看板触发的 SIZE SPRAWL 和 TEXT WALL。真缺陷（如 chengdu 页脚）不算误伤。
5. **SKILL.md 送达调整**
   - 把设计相关的关键操作知识挪到 agent 实际会读到的段落，或做成命令输出。总字节数不增加。
   - `check_skill_lossless` 必须通过。

每项都按 TDD 写测试，并在至少一份它没有针对调过的 deck 上验证。

### Phase 3 — 守门与复测

- 守门脚本 `design_benchmark.py`（名字是我的决定）。输入一个渲染好的 deck，输出 Phase 1 的那组自动指标。
  - 对比对象是**最接近的那份基准**（按用途或视觉语言匹配；没有可匹配的就和全部基准逐份比），不用全局的最小–最大区间，因为那样宽到什么都抓不住。
  - 基准指标快照存进仓库（小 JSON，中英文 24 份都存），不把 pptx 放进主仓库。
  - 它是 advisory：大改后由人或开发 agent 手动跑，不接入 CI 阻断，也不接入用户运行的 `deck_cycle`。（我的决定）
- 测试：对快照做一致性检查，并把 Phase 2 的每个新检查在基准快照上跑一遍，不能误报。
- 文档：在 file-inventory 和开发者文档里写明"大改后重跑 4 份 brief + design_benchmark"的流程。
- 复测：用 Phase 1 同样的 4 份素材、同样的方式重跑。盲评和指标的改前改后对照放进同一个 Desktop 文件夹。

## 5. 留给实现者决定的

- 抽取素材文档的具体格式（docx 还是 md）、图片命名。
- 盲评提示词的措辞。必须盲评、交换左右、给理由。
- 骨架相似度的具体算法和阈值（以"12 份全过、已知单调 deck 被抓"为准）。
- 组件总览图的版式。
- 推荐脚本的输入解析细节。

## 6. 成本与时间（估计）

- Phase 1：9 个实跑，分两批并行，约 80 分钟墙钟；加评审和整理约 20 分钟。
- Phase 2：取决于缺口数量。
- Phase 3：复测再跑一轮，约 40 分钟。
- 全部用 Sonnet subagent 和 codex 订阅，不产生付费 API 开销。
